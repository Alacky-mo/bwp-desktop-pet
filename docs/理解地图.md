# 理解地图：百闻牌桌宠（给自己看的）

不写代码细节，只写「东西在哪、名词是什么意思、数字是从哪来的」。

## 名词表

| 名词 | 说的是什么 |
| --- | --- |
| npk | 网易 NeoX 的资源容器（魔数 `NXPK`，条目数在偏移 4；0x14 处那个字段**只能当参考、不能当数据区结尾**），一条一条 zlib 压缩 |
| skel | Spine 的**二进制骨架**文件，里面是骨骼/插槽/动画关键帧，不含图 |
| atlas | Spine 的图集描述文件（纯文本），说清每个 region 在页图的哪一块 |
| page / 页 | atlas 引用的那张大图（这里是 ASTC 4×4 的 KTX，解码后才看得见）。**页 id 就是联系表上给你看的编号** |
| region / slot | region 是页上的一块图，slot 是骨架里挂这块图的槽。两者名字通常一样 |
| plist | TexturePacker 导出的图集描述（Apple plist XML，在 `gui.npk` 里以 `.xml` 出现）。写了页名 `realTextureFileName` 和每个 region 的矩形——**gui.npk 里唯一有名字的东西**，头像框的命名全靠它 |
| alias / rotated | plist 里 `textureRect` 为空的 region 是别名（跟别人共用一块图，没有自己的矩形）；`textureRotated=true` 的在页上占的是**宽高互换**的那块 |
| 画布 | 骨架自己的逻辑尺寸。式神立绘 600×600 或 2265×1567，Q 版头像只有 110~230 单位 |
| 姿态词 | `idle1/battlestand/combat1/casting1/born_break`，式神立绘那五个动作槽 |
| 表情词 | `happy/sad/surprise/thinking/smile/angry/serious/emotion1..6`，Q 版头像的换脸动作 |
| census | 把所有骨架的「能不能解析/画布多大/有哪些动画名/用了哪些 region」摊成一张表，词汇表就是这么来的 |
| twins | 一套 region 名被几个 atlas 共用。>2 就说明认不出这是谁的骨架，直接跳过 |
| bnk | **Wwise** 的 sound bank（`res/wwise/<单元>.bnk`），语音就在这里面。段是 `BKHD/DIDX/DATA/HIRC`，2021 一代（`BKHD` 版本 125） |
| wem | 同目录下的散装音频（文件名就是 media id）。少数语音的音频不在 bank 里，靠这个外流文件 |
| discrete | `meta/subpack_version.json` 里的 `type`，意思是「按需下载的散装文件」，**不是** npk 里的一条 —— 所以语音在 npk 里翻不到 |

## 素材到底有多少（都是实测数）

- **式神立绘**：`spine_hero1~3` = 909 个可解析骨架（253/362/294）。固定五槽动画约 650 个，
  另有 252 个只有 `born` 的入场骨架（只能当入场素材，当不了桌宠本体），少量拼写变体。
  895/909 能打包，其中 247 个要合并 2~4 个 atlas，14 个的部件在别的包里。
- **Q 版表情头**：`spine.npk` = 1256 个骨架 blob、1236 个可解析，词汇表和 spine_hero 完全不同。分四组：
  - `emotion` **163 个**：真的会换脸的头像/半身，其中 104 个是 `happy/idle/sad/surprise/thinking` 标准五连，
    19 个是 `emotion1..6`，8 个带 `_mouth_say` 口型件（口型没接，桌宠没有语音）。
    画布 110~230 单位。不知火在这组里有 4 个（`buzhihuo_1127` 正脸、`_yihua_2717` 拿扇子、`_pifu_3604/3608` 小 Q 版）。
  - `head` 305 个：≤200 单位的小 idle 件（圆形**头像框**、庭院/活动装饰）。已按名字裁出 41 张带框的
    `crops/spine/*kuang*.png`（RGBA、中心透明、159~667 见方），联系表在 `out/frames_sheet.png`，
    能直接当桌宠的一层；但它们是单帧 region，要动就得回读 `t/spine/NNNN.bin`。
    真正的**游戏 UI 头像框**（对战/聊天/称号框）不在 spine 包里，在 `gui.npk`：
    角色头像框是 `_charframe0.png` 那一页 10 张（`crops/gui_charframe/`），
    UI 上带 `kuang/head/touxiang` 的件裁了 117 张（`crops/gui_frames/`），名字是从包里的 plist 配的，
    见规格「gui.npk 的命名规矩」。`bigtexture.npk` 那 2502 张 1024 页跟这批框无关（没跑过配对）。
  - `deck` 297 个：`deck_idle`，1400×787 画布 = 图鉴卡面。
  - `other` 254 个：剧情立绘、`sandtray`、特效。
- **玩家头像本体是静态图**：`texture_card_small1.npk` = 2695 张 256×256 ASTC 图标。
  动态头像这条路是靠上面那 163 个表情骨架走通的。
- `char.npk` 是 NeoX 的 xml/RGIS 配置，不含 spine。

## 一条动画名是怎么上屏的

```
skel 里的动画列表
  → Spine.Spine.AnimationNames
  → BwpHero.Actions 按「命中表情词?」分流，把交互映射成具体动画名（Idle/Alert/Attack/Cast/Entrance/Sleep + 表情池）
  → 交互事件（Click/DoubleClick/Scroll/DragBegin/SleepStateChange/Update 随机）设 CurrentAnimation
  → PlayOnce 播完自动 AddAnimation(idle) 回待机
  → SFML 渲染，槽名前缀过滤掉战斗背景层，PMA 决定是否反预乘
```

看效果不用开界面：`bwp-animator-test drive` 就是这个链路在真模型上无头跑一遍，把每步动画走向打出来。

多只同屏还是多只轮流出，是 `SpineSlot.ActiveSlot` 说了算：`-1` 时十个槽位当一个角色的图层，
`>=0` 时只放行那一格（`Render`/`Update` 双双门控），槽位就成了名册，一格一只。
`BwpHero` 不知道这事——它照旧遍历所有槽位设动画，没出场的格子既不画也不走帧，改了也看不见。
所以换人只要挪 `ActiveSlot`，三只骨架在启动时全装载好了，切换是瞬时的、不重新解包。

## gui.npk 里一张图是怎么拿到名字的

```
npk_text.py  → t/gui_text/NNNN.xml        plist（TexturePacker 导出的图集描述）是有名字的文本条目，照样倒得出来
gui_plist_index.py → out/gui_atlas.json   页名 + 每个 region 的矩形（两种方言都读）
npk_scan.py  → out/gui_scan_all.tsv       每条图片 blob 的 idx/偏移/尺寸/格式，先不解码
gui_page_map.py                           尺寸对得上 → 粗网格 IoU 提名 → 整分辨率 content_fit 判决 → 一对一认领
                                          → 按资源名裁成 crops/xxx/yyy.png
```

所以「破不了 TOC」不等于「拿不到名字」：网易把 plist 和图一起打进包，plist 走的是文本条目，
TOC 加不加密跟它没关系。反过来，**页名不唯一**（同一张 `_activity3.png` 有好几个 plist 版本在引用），
所以索引的键是 xml 文件名，认领时必须一对一，否则两个版本抢同一张页会各裁出一半对的图。

## 语音在哪、能不能对上表情（2026-10-28 查清，2026-10-29 补上「能听、能转字」）

```
voice_pull.py ls                             设备 Documents/res/wwise 的清单 → out/voice_wwise.tsv
voice_pull.py pull vo_emotion / vo_battle …  按前缀拉 bank 到 voice/raw/，逐个核对远端字节数
voice_pull.py wem                            按 voice_bnk 生成的外部 media 清单拉 <media id>.wem
voice_bnk.py parse voice/raw -o out/voice_clips.tsv   解 BKHD/DIDX/DATA/HIRC → 逐条语音 + 逐单元汇总
voice_bnk.py slots voice/raw --cat emotion   查各包之间共不共用 event/分组 id（共用了才谈得上「分槽」）
voice_index.py                              三方对齐：清单的单元 × 设备上的包 × 表情骨架拼音 → out/voice_roster.tsv
voice_decode.py --cat emotion               bank → 能双击的 wav（vgmstream），出 out/voice_wav.tsv 记每句精确时长
voice_asr.py --cat emotion --per-line --resume  本机 whisper 逐句转成日语原文 → out/voice_lines.tsv（可断点续跑）
voice_group.py [--unit <单元>]              把转写按 Wwise 容器摊开看（用来验「容器=情绪」这条假设）
voice_probe.py --cached --cat emotion --phrase <日语>   拿耳朵听到的一句反查素材：先在已转写的表里比（秒出，不跑模型）
voice_probe.py --unit <单元> --only-empty --phrase <日语> 再把没转出字的那几条重跑两遍（无提示+带提示）逼出原文
```

- **量**：清单里 810 个 `vo_*` 单元（battle 481 / biography 155 / emotion 144 / street 30），设备上落了 784 个
  共 226 MB，本地全拉下来了（+ 189 个外部 `.wem`，263 MB，都在 `voice/raw/`，已 git 忽略）。
  解出来 **12,675 条语音**，估 1,031 分钟；表情语音 139 个单元 3,858 句、估 77 分钟。
- **「一个单元几句」是读得出的**：一个式神的表情包 = 21~22 条（中位 22，区间 2~70），
  战斗包 4~7 组、传记包 1~3 句长音频（传记的音频多半在外部 `.wem`，包里只有 id）。
- **「哪一句配哪个表情」在包的结构里读不出来**，三条独立证据（今天又用 `voice_group.py` 复核了第 3 条）：
  1. bank 里没有字符串表（没 `STNG`/`PLTg` 段），event/media/sound 全是一串 32 位数字 id；
  2. `slots` 实测：表情包里 3,631 个 event id、3,668 个 media id **全部只出现一次**，
     190 个分组 id 有 189 个只属于一个包 —— 没有任何跨角色的「开心槽」这种公共 id 可以对齐；
  3. 一个包内 21~22 句全挂在**同一个**随机容器下（138 个包里 135 个只有一组），本身就不按表情分堆。
  而对上骨架的那 98 个单元，是「中位 22 句抢中位 5 个表情动画」，就算知道槽位也是一对多。
  选择表在 `script.npk`（条目非明文，已确认倒不出文本，按规矩不去破）—— 所以配对这条路只能走**语义**：
  先把每句转成原文，再按意思归到该角色骨架有的动画名上（下面两条是这条路的两个前提，2026-10-29 都验到了）。
- **能听了，也能转成字（2026-10-29 补）**：vgmstream r2168 能**直接开 Wwise 一代 bank**
  （`-s 1 -S 0 -o "?n.wav"` 一个 media 出一个 wav，`?n` 就是 media id，和包外散装 `.wem` 同名），
  编码报 **Custom Vorbis** —— 之前写的「本机没有解码器所以听不了」「要先把 media 从 DATA 段搬出来」都作废，
  `voice_wem.py` 因此删了。表情语音 139 个单元解出 **3,857 个 wav / 1.28 小时 / 314 MB**（`voice/wav/`，git 忽略），
  一条都没解空。顺带把时长模型验死了：**估时误差中位 0.0%、最大 0.1%**，`数据段/平均字节率` 可以当尺子用。
  判「解空」要用**峰值**不能用「有声帧占比」——短句喊完就是静音尾巴，19 条差点误报成静音。
- **配音是日语，不是中文**（拿传记旁白实测：自动判定全 `ja`、置信 0.98~1.00，转出来是通顺日语；按 `zh` 喂一句都出不来）。
  本机 faster-whisper `small` + CPU int8（没 CUDA，只有 Intel Arc）装在 `~/venvs/asr`，模型走 hf-mirror 且必须
  `HF_HUB_DISABLE_XET=1`。**用逐条法不用槽位法**：whisper 时间戳有 0.2~0.5 秒漂移，而表情语音一句中位才 1.07 秒，
  整单元拼一条虽快 10 倍，实测会把一句撕进邻句；逐条换「这行字就是这句音」的绝对对应，实测 2.7~5 秒/条
  （试跑那 22 句 2.68，全量跑起来 5 秒/条），1.28 小时音频约 4~5 小时，单元内每 25 句落一次盘、心跳写日志。
- **容器不是情绪**（`voice_group.py` 实测，这条假设死了）：139 个表情单元总共只有 236 个容器组，
  一个单元基本就一个组（`vo_emotion_103_buzhihuo` 的 22 句全在 `896183464` 里）——容器就是「这个包的播放列表」。
  真正能承载情绪标签的是**表情骨架自己的动画名**：名册对上骨架的 98 个表情单元，动画名高度收敛在
  `surprise/sad/idle/thinking/happy`（各 92~98 个单元有）+ `smile/angry/serious` 这几个槽位，
  所以配对的做法是**读转写做语义判断，把每句归到该角色骨架有的那几个动画名上**。
  不知火那 22 句试跑出来的转写正好铺满这套槽位：问候 / 谢 / 认同 / 拒 / 惊 / 丧 / 傲
  （逐句原文是游戏语音的转写，按裁定不进版本库；要对照只读本机未跟踪的 `out/voice_lines.tsv`），
  4 句没出字的是 0.5~1.1 秒的短音（多半是非台词的气声/笑）。
- **用户在游戏里数的「一个头像两句专属：问候 + 称赞」对不上不知火的包**（2026-10-29 用 `voice_probe.py` 比过）：
  不知火只有 `vo_emotion_103_buzhihuo`(22 句) 和 `vo_emotion_167_buzhihuo`(31 句)，两个单元**已全部逐句转写完**，
  拿用户听来的那两句（一句问候、一句称赞）去比，53 句里最高相似度只有 **0.22**（都对不上）；
  连 10 条没转出字的都重测过一遍（无提示 + 带提示两次），出的全是气声和笑那一类，
  带提示也没被幻听成目标句 —— **「这两句在不知火包里」这条路是封死的**。
  不知火自己有的问候/称赞是 5 句：问候落在 `103#10`(0.64s，同一句在 `167#4` 出 0.81s)、`103#21`(0.94s)、
  `167#22`(0.96s)，称赞落在 `167#2`(0.92s)、`167#12`(0.56s)（哪句是什么，查本机不入库的那张表）。
  而这两句**确实在库里，只是挂在别的角色上**（已转写的 20 个单元 536 句里，角色只认包名里的拼音，中文名没确认过就不写）：
  「好久不见」那一类在 `170_bianhua` / `118_yimulian` / `121_quanshen` / `177_longyechaji` / `178_huang` /
  `111_cimutongzi` 六个单元里各有一句（词尾三种收法）；赞美那一类在 `119_shuweng`(两句) / `177` / `178` /
  `126_ciqiqingwa` / `105_datiangou` / `107_yingcao`。

  所以剩下两种解释没排除：① 用户听的那个头像复用的是共享池 —— `vo_emotion_2`(366 句，正在转写，优先跑的就是它)；
  ② 听错了角色或词尾。要定案得靠人耳：命中的几条 wav 路径在上面，直接去听。
- **配对落地成「规则表 + 套规则的脚本」**：`voice_emo_rules.tsv`（规范化日语 → 中文意思 → 动画名，判断只写在这里）
  + `voice_emo_map.py`（套规则出 `out/voice_emo_sheet.tsv` 联系表；`--audition` 再把 wav 硬链成
  `voice/audition/<角色>/<表情>_<序号>_<原文>.wav` 供肉眼抽检）。匹配用的规范化 =
  片假名折平假名 + 按 **Unicode 类别**剔标点 + 去促音 `っ`，**长音 `ー` 保留**（抹掉它「答应」那一类和「沉吟」
  那一类会撞成一条，答应的「嗯」和沉吟的「唔……」翻车；第一版手抄标点字符表漏了半角 `!` 和 `…`，所以别手抄）；

- **引擎侧只加了「切脸时开口」这一条线（2026-10-29）**：`TinyEngine/src/Speaker.cs` 从空壳改成 winmm
  `PlaySound(SND_FILENAME|SND_ASYNC|SND_NODEFAULT)` 播放器 —— 选 winmm 是因为 TinyEngine 没开 `UseWindowsForms`，
  `System.Media.SoundPlayer` 用不了，而素材就是单声道 16bit PCM wav，不值得为它引第三方库。

  `Say` 把 manifest 按 `<skelPath 所在目录>/voice/_manifest.tsv` 找包（没包就静音、并缓存空表不重复读盘），
  动画名比对复用 `BwpHero.Normalize`（所以 `idle1`/`idle` 这种写法差异不影响开口），每个「骨架+表情」一条洗牌队列，
  **一轮播完才重洗**，所以不会连着听同一句；窗口隐藏和入睡时 `Stop()`。`Normalize` 从 `Actions` 内层类提到 `BwpHero`
  上当 `internal static`，就是为了给 Speaker 用。
  实测：`dotnet build DeskSpine.sln` **0 警告 0 错误**；用 ctypes 直接叫同一个 `winmm.PlaySoundW` 播包里最短那条
  （`idle_2_665754525.wav`，0.285 秒）返回 1、同步耗时 1.0 秒 —— 文件确实放出来了。**但「桌宠点一下有没有出声」只能由用户复验。**

## 踩过的坑（别重犯）

- **`\r\r\n`**：npk 里的文本条目自带 CRLF，按文本模式写盘会变成 `\r\r\n`，atlas 每行之间多一个空行，
  Spine 直接报 "Error reading atlas file"。现在按字节写。
- **表情词和 `idle` 撞名**：归一化会抹掉数字，`idle1`→`idle`，所以不能用「有 idle」判表情骨架。
- **配置被静默冲回**：模型加载失败时程序保存的是内存里的旧路径，GUI 里点了也可能没生效——直接看 json。
- **3.8 静默失败**：选错运行时不报错，最后死在 `DefaultAnimationName`。
- **ASTC 解码出来是 BGRA，不是 RGBA**：`texture2ddecoder` 对每种格式都返回 BGRA，按 RGBA 读等于红蓝整通道互换，
  全库素材偏冷偏紫。之前把它误判成「不是解包错，是 PMA+冷色特效件+运行时暖色」，那条只解释变暗，解释不了互换。
  自检不用对游戏截图：数亮肤像素（V>170）里 R>G>B 和 B>G>R 的比，游戏自带原生 PNG `t/loading` 是 2.79×，
  比值小于 1 就是通道反了。
- **静态裁切低估素材**：PMA + 冷色特效件 + 运行时才加的暖色，让 crop 比游戏里暗、比游戏里冷。判断观感必须跑动画。
- **动画名拼错会让表情静默失效**：`maozhanggui_sp_yihua` 的惊讶写作 `suprise`（全库唯一一处），
  进不了 `MoodWords` 的门，表现为拖拽和单击撞同一张脸。现在 `Normalize` 顺手把它归一到 `surprise`。
- **adb 路径被改写**：Git Bash 里要 `MSYS_NO_PATHCONV=1`。
- **Wwise HIRC 对象头猜了四遍才对**：`[u8 类型][u32 长度][u32 id][长度-4 字节的体]`，步长 `5+长度`；
  判据是「走完最后一个对象正好落在段尾」（逐角色包 68/68 落在 2066/2066，共享包 547/547 落在 20426/20426）。
  只要没落在段尾，后面数出来的句数全是废的 —— 别拿「能读出几个对象」当过。
- **语音 media 的 WAV 壳长度不是常数**：表情包是 94 字节（12 RIFF + 8+66 fmt + 8 data），
  战斗包多了 `JUNK`+`akd ` 两个块变 120 字节。写死 94 会让 33 个战斗/玩家包集体判失败，
  所以壳长要从 chunk 走一遍量出来（`wav_info` 返回 `start`）。采样率和平均字节率也是**按条不同**，别当全局常数。
- **Sound 体里那个长度字段在外部 media 上不是字节数**：传记包很多句的音频在 `<media id>.wem` 里，
  包里那个 u32 和 `.wem` 实际大小 189 条里 0 条对得上 —— 包外的一律不报字节数、不估时长。
- **bank 落盘尺寸 ≠ 清单 size**：`vo_emotion_103_buzhihuo` 设备 153,728、清单 153,880。
  清单记的是下载包体，bank 是序列化后的，**核对只能按名字，不能按字节数**。
- **0x14 当数据区结尾用会静音吞页**：`gui.npk` 的 toc_start 之后还有 192MB，里面 carve 得出 **67 块**
  （44 张 2048 的 atlas 页 + 16 PNG + 7 JPG），旧 `carve(..., toc_start)` 每次解包都不吭声地跳过它们。
  其余 10 个包把 `toc_start..EOF` 单独 carve 一遍是 **0 块**（那就是 TOC 本身），
  所以**只有 gui.npk 受过这个影响**，spine 那批的既有结论不用重跑。
- **ETC 解码函数只收三个参数**：`decode_etc2a8(data, w, h)`，ASTC 才要 block 尺寸；多传 bpp 直接 `TypeError`。
  还有 `0x9278`（ETC2 RGBA8_EAC）没登记进 `ETC_FMTS` 时，整页被当「不认识的格式」跳过——同样是静音丢失。
- **粗网格 IoU 不能当判决**：2048 的密页占位并集几乎全满，不同页的 IoU 全是 0.9x，提名出来的组合看着都像。
  判决必须回到整分辨率的「内容不许溢出声明格子 / 声明格子不许是空的」，再加一对一贪心认领。
- **一次性手写的索引脚本会静默少数据**：`out/gui_atlas.json` 最初是临时命令生成的，漏掉每份 plist 的**第一帧**
  （369 份中招），又把第二种 plist 方言（cocos2d 的 `frame`/`sourceSize`，不是 `textureRect`）的 region 当成
  「没有矩形」全丢（675 个）。后果直接可见：`_charframe0.png`（10 张真正的角色头像框）配不上任何页。
  补全后 fit=1.0000 一把配上。**凡是喂给判据的索引必须有名字、能重跑的脚本**，不能是聊天记录里的一条命令。
- **plist 的 trim 不紧**：别拿「内容必须贴到矩形四条边」当校验，`charframe/0001` 的矩形 115x102、内容只有 99x94
  （`spriteOffset` 说明内容在原始 128x128 画布里是偏心的）。裁出来四周留白是正常的。
- **rotated 的 region 在页上宽高互换**：448 个，mask 要换回来才不漏判；但转回去的方向没实测过，
  `gui_page_map.py` 现在是打印警告并跳过，不猜。
- **`WorldBounds` 比看得见的身体大 8~13%**：它并的是整个图集矩形 region，而表情图集全是
  `size==orig / offset:0,0`（900+ 个 atlas 一个裁切的都没有），可打包出的 PNG 在 region 里还留着大片透明留白
  （不知火的 `youfa` 57x173，其中 127px 是空的）。虚增全垫在下半身，拿包围盒中心当脸，环就会既大又往胸口坠。
  所以图层要离屏拍一发热量实测「画出来的方框」（`Silhouette.OpaqueBox`），别信包围盒。
- **剪影里最厚的圆不一定是头**：千姬胸口那坨半径 30 > 头的 28，纯取最大内接圆会量到胸口；
  改成「只在画出来的方框上面 60% 里取最厚的圆盘」才对（`Silhouette.HeadMass` 的 `HeadBand`）。
  早先用「和最大圆差不过一成的候选里取最靠上那坨的质心」也试过来，但它在 256 和 512 两种分辨率下会选到不同的团，
  验收自己跟自己对不上——几何先验比厚度容差稳。

+ `SpineRenderWindow` 注册 `scene.Renderables["pomodoro"]` 并覆写 `SleepLimit()`。

P1 落地的形状（应用侧，不碰引擎）：`Config.cs` 多一个 `PomodoroConfig` 段（四个时长 + 不许打瞌睡 + 到点弹气泡），

`ConfigForm.cs` 托盘插「番茄钟」一项（开始/暂停/跳过/停止 + 顶部那行现读的状态字）、
`focusTimer` 每秒只看 `TransitionId` 变没变来决定弹不弹气泡，`ConfigForm.Designer.cs` 多一整页「番茄钟」六个设置项。

- **`Config.Load` 是逐段手抄的**（`SystemConfig`/`BasicConfig`/`SpineConfig` 三行 `if (… is not null) X = config.X`），
  新加一段忘了补这行就是「存得进去、读不出来」，而且默认值刚好和设置窗显示的一样，肉眼完全看不出。
  **是无头判据抓到的**：`desk` 里第一层用一组和默认值全不同的数（17/3/23/6/关/关）存回读，第一次跑直接报「否」。
- **判据不能依赖进程活多久**：`ConfigForm` 构造函数把 1 秒的气泡计时器武装上了，无头跑 `Program.SpineWindow` 是空的，
  计时器一 tick 就是 NRE —— 崩不崩取决于进程有没有撑过那一秒。反射拿到 `focusTimer` 先 `Stop()`，结果才跟时间无关。
- 同理，`Value` 的 getter 在位置/尺寸那几个框**锁着**时会去读 `Program.SpineWindow`（`Enabled ? 控件值 : 窗口现值`），
  无头就按「用户已解锁位置」那种状态跑：先把那几个框 `Enabled = true`，再跑 `ConfigForm_Load` 绑下拉框的 DataSource
  （不绑，getter 拿 `(SpineVersion)null` 强转直接抛）。
- **配置手改得出越界的数**：`NumericUpDown` 赋越界值是直接抛的，所以 setter 那边先 `Math.Clamp` 到控件自己的两头。
  判据喂 999 和 -5，读回来该是 180 和 1。
- **专注段闭嘴（用户复验 1、2 项通过后提的新要求）**：`Animator.Muted` 只挡 `BwpHero.PlayOnce` 里那句 `Speaker?.Say`，
  **表情照换** —— 状态是表情给的，打扰才是语音给的。`Pomodoro.Update` 的顺序是「先解锁 → 换脸 → 再按当前阶段静音」，
  于是开工/到点/回来这三句边界提醒都听得见，只有**段内的自言自语**（静置随机、点击、报时）被按住。
  副作用要记着：**整点报时那句语音在专注段里也不出声**（气泡照弹），这是同一条规则的必然结果。
  `Muted` 和 `Speaker.Enabled`（用户自己的总开关）是两回事，别混用；中止不排 pending，靠每帧对齐那一行才解得开。
  判据不用竖着耳朵听：`Speaker.rotating` 的键只在真抽到一句时才建，`pomodoro` 模式现在 39 项。
- **`TinyEngine` 是 C# 12**：`Target?.Muted = false` 这种**null 条件赋值**要 C# 14，会直接编不过，得先取局部变量再判 null。

- 计时必须用**挂钟**不能用帧 delta 累计：窗口 `visible=false` 时 `UpdateFrame` 根本不跑（`LayeredRenderWindow.cs:97-105`），
  用 delta 会在隐藏/锁屏时漏时间。`Pomodoro` 的时间源做成可注入的 `Func<DateTime>`，为的就是无头快进验收。
  **藏窗口是真会发生的**：判据里藏 60 分钟回来，一帧按挂钟逐段补 4 段、今日计数补到 3，但只交**最新那一张脸**
  （`pending` 只留最后一次切换）——既没丢时间，也没在一帧里连响四句。
- **只有挂钟会把「合盖」当成「专注」，所以要双轨**（2026-10-29 化用 Catime，已落地）：`Pomodoro.Mono` 是第二只钟，
  默认 `Win32.GetUnbiasedElapsedTime()` → `QueryUnbiasedInterruptTime`。选它是因为微软文档写明**它只计工作状态的时间**，
  而同类的 `GetTickCount64`/`Environment.TickCount64` **文档明写含休眠**，当不了这只钟（这条是查文档定的，不是猜的）。
  每帧比 `挂钟增量 - 单调增量`，差值 > 2 秒就认定中间睡过，把 `phaseEnd` 往前挪这么多 —— **平移 deadline 而不是逐段补**，
  于是合盖六小时回来还停在原来那一段、剩余还是睡前的 18 分钟，不冒出 14 个番茄。阈值 2 秒是因为挂钟粒度约 16ms、帧隔 33ms。
  三个坑各自有判据：①**暂停中的那一段不吃时间，所以绝不去加 `pausedLeft`**（加了会把 3 分钟睡成 3 小时）；
  ②`mono < monoAnchor` 就当没看见（退回值和异常值都在这挡掉）；③**顺序不能反**：先平移再 `CatchUp`，
  反过来就是「先补出十几个番茄、再挪一个已经作废的 deadline」。
- **挂钟被往回拨（改时区/NTP/手动调表）时按新表走，但剩余封顶在这一段本身**：`Remaining` 和 `phaseEnd` 都过 `Bound`，
  所以既不会说漏「剩一小时」，也不会倒着数出负数。这是 `pomotroid`/`goodtime` 那套「宁可重锚也不信挂钟」的最小版。
- **这只钟在这台机器上实测有效**：判据里反射读一次，`醒着 205.6 小时 / 开机 339.4 小时` —— 差的那 133 小时就是开机以来睡掉的，
  说明 P/Invoke 真解析到了，而不是静默走了退回分支（退回了会返回公元 1 年起算的巨大 tick，判据当场红）。
- **入睡边界的写法被实测纠过一次**：原来靠「这一帧过阈值 && 上一帧没过」判沿，阈值一旦被顶成 `float.PositiveInfinity`
  就再没有「上一帧低于阈值」那次比较，**睡着的宠物点了开始番茄也不会醒**。改成窗口自己记 `sleeping` 标志，
  阈值是每帧现读的 `SleepLimit()`，顶成无穷大就当帧唤醒。
- **控制项只置标记，脸等下一帧**：`Start()` 之后立刻读 `CurrentAnimation` 读到的是上一张脸（判据第一版就这样误报 FAIL）。
